# Подготовка PR и синхронизация develop/master

## Почему возникают конфликты

PR в этом репозитории вливаются **squash-мержем**: в `master` попадает один новый
коммит с текстом PR, а история `develop` с ним родства не имеет. Дальше любая
правка того же файла в `develop` конфликтует с `master`, хотя фактически это
один и тот же код — просто в разных коммитах.

Проверка, которая ловит это заранее:

```
git merge-base --is-ancestor origin/master develop
```

Истина — GitHub конфликтов не покажет. Ложь — PR откроется «с конфликтами»,
даже если все файлы на вид одинаковые.

## Порядок перед открытием PR

1. `git fetch origin` — иначе проверка идёт по устаревшему `origin/master`.
2. `git merge origin/master` в `develop`.
3. Конфликты решать **в пользу `develop`**, если `master` — снимок той же работы.
   Как убедиться: `git log --oneline origin/master..develop` показывает, что
   в `develop` лежит новее; если в `master` есть чужие коммиты, сначала смотреть
   `git log --oneline develop..origin/master`.
4. Проверить, что маркеров не осталось (поиск `<<<<<<<` по проекту).
5. Прогнать проверку (`npm run test:headless`, `check.cmd`).
6. `git push origin develop` — после этого PR мержабелен.

## Грабли

- **Не переписывать историю ветки, по которой открыт PR.** Force-push меняет базу,
  GitHub пересобирает PR и показывает конфликты там, где их не было.
- **Разрешение конфликта — это не «взять свою версию» вслепую.** Сначала выяснить,
  чей снимок новее; при squash-мерже «наша» сторона почти всегда верна, но при
  чужих коммитах в `master` — нет.
- **Локальный зелёный прогон не гарантирует зелёный CI.** Платформы разные
  (8.5.4 локально, учебная поставка 8.3.27 в CI), и различия движка проявляются
  только там. После мержа в `master` смотреть билд.
- **Текст PR писать сразу пригодным для squash-коммита**: заголовок одной строкой
  и разделы «что изменилось», «почему», «проверено», «как проверить», ссылки
  на issues. Он станет сообщением коммита в `master`.
